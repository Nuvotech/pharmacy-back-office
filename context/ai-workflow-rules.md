# AI Workflow Rules

## Approach

Build the pharmacy system incrementally, using a spec-driven workflow. The context files define what to build
and how to build it, and record progress so far:

- `ps-back-office-overview.md` — the admin back office (and manager app): what it does, for whom, scope and
  success criteria
- `ps-counter-overview.md` — the sales counter app: what it does, for whom, scope and success criteria
- `architecture.md` — stack, system boundaries, storage model, sync, auth and invariants
- `code-standards.md` — conventions for PHP/Laravel, Inertia/React, Expo and the device API
- `design.md` — the only source for styling: tokens, typography, components, status colours
- `progress-tracker.md` — the current phase, units done and in progress, and open questions

Always implement against these files; do not infer or invent behaviour from scratch. Work follows the project
phases in order: Phase 1 (back office), Phase 2 (counter app and sync API), Phase 3 (stock operations),
Phase 4 (reports), then the manager app. A unit of work is one item in `progress-tracker.md`.

Within a unit, build from the inside out: migration (if any) → `app/Domain` service with its tests → controller
or API endpoint → screen. Logic that touches stock, money, FEFO or sync is written test-first.

## Scoping Rules

- Work on one feature unit at a time
- Prefer small, verifiable increments over large speculative changes
- Do not combine unrelated system boundaries in a single implementation step: `apps/server`, `apps/counter`,
  `apps/manager` and `packages/sales-core` are separate boundaries
- A unit that needs both a server change and a device change is done in two steps: the server API first, with
  its tests and updated `api-types`, then the app that uses it

## When to Split Work

Split an implementation step if it combines:

- Server changes and mobile app changes
- A change to the stock ledger, FEFO allocation, sync ingest or money maths together with UI work
- A database migration together with an unrelated feature
- Several unrelated API endpoints or back-office screens
- A refactor together with new behaviour
- Behaviour not clearly defined in the context files

If a change cannot be verified end to end quickly, the scope is too broad — split it.

## Handling Missing Requirements

- Do not invent product behaviour not defined in the context files. This includes stock rules, prices,
  rounding, alert thresholds, report contents and French wording shown to users.
- If a requirement is ambiguous, resolve it in the relevant context file before implementing
- If a requirement is missing, add it as an open question in `progress-tracker.md` before continuing, and work
  on a unit that does not depend on it
- Screen layouts follow the Pharmacy POS Screens designs and `design.md`; a screen with no design is an open
  question, not something to design freely

## High-Risk Areas

Changes to these need tests written first, and a note in `progress-tracker.md` saying what changed and why:

- `app/Domain/Stock` — the stock ledger and lot quantities
- FEFO allocation, on the server and in `packages/sales-core/fefo`
- `app/Domain/Sync` and `packages/sales-core/sync` — ingest, de-duplication, reallocation, outbox
- `packages/sales-core/money` and anything that converts between CDF and USD
- Authorization: Policies, token abilities, roles

## Protected Files

Do not modify the following unless explicitly instructed:

- Migrations that have already been run in any shared environment — add a new migration instead
- `apps/server/resources/js/Components/ui/*` — generated shadcn/ui components
- `apps/server/resources/js/types/generated.d.ts` — generated from PHP; regenerate it, never edit it by hand
- `docs/api/*` — generated by Scribe; regenerate it
- `design.md` — styling decisions are made there by a person, not during implementation
- `.env`, `.env.*`, signing keys, `eas.json` credentials and any secrets
- `vendor/`, `node_modules/` and any third-party library internals
- Lock files (`composer.lock`, `package-lock.json`) — change them only through the package manager, and only
  when adding a dependency was agreed

## Commands Never to Run Without Explicit Instruction

- Anything against production: deploys, `php artisan migrate` on the server, database access
- `php artisan migrate:fresh`, `db:wipe` or any command that deletes data outside the local database
- `git push --force`, rewriting shared history, or deleting branches
- Installing new dependencies

## Keeping Docs in Sync

Update the relevant context file in the same change whenever implementation changes:

- System architecture, boundaries, sync or auth → `architecture.md`
- Storage model or schema decisions → `architecture.md` (plus the migration)
- Code conventions or standards → `code-standards.md`
- Feature scope or user flow → `ps-back-office-overview.md` for the back office and manager app,
  `ps-counter-overview.md` for the counter app (a change affecting both updates both)
- Any device API change → regenerate `docs/api/` and update `packages/api-types` in the same step
- Progress, decisions and open questions → `progress-tracker.md`

## Before Moving to the Next Unit

1. The current unit works end to end within its defined scope
2. No invariant defined in `architecture.md` was violated
3. `progress-tracker.md` reflects the completed work and any new open questions
4. Server checks pass in `apps/server`: `php artisan test`, `vendor/bin/pint --test`,
   `vendor/bin/phpstan analyse`, and `npm run build`
5. `php artisan migrate:fresh --seed` runs cleanly on the local database
6. For TypeScript in the mobile apps and packages: `npx tsc --noEmit`, lint and `npm test` pass
7. If the unit touched selling or sync, the affected items of the Phase 2 offline test checklist pass on an
   emulator or the real tablet
8. If the unit touched the device API, `docs/api/` and `packages/api-types` are regenerated and match the code
